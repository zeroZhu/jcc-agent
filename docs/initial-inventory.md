# 己方初始持牌基线

当前纯 OCR 已能读取商店英雄名、价格和部分详情文字，但录像中的星级是图标、空格没有稳定文字。程序不能把“没有读出名字”变成“空位”，也不能把星级未知当成一星。因此，当前自动买牌链路需要一份**由人核对的当前持牌基线**，再根据已确认购买和普通合成事件持续更新。

这是当前纯 OCR 限制下的过渡输入路径，**不是自动初始化已经完成**。模板、演示数据、历史录像中的持牌和上一局的导出都不能直接充当现在这局的事实。

## 文件与字段

复制 `configs/inventory.template.json` 为本局单独的文件，例如 `configs/local.inventory.json`。模板预填 `board_0` 至 `board_27`、`bench_0` 至 `bench_8` 共 37 个位置，全部为 `unknown`、置信度 0，且 `ordinary_merges=false`。它不会授权购买或刷新，也不能直接用于执行模式。

| 字段 | 如何填写 |
|---|---|
| `board`、`bench` | 每个位置必须独立核对；键必须与本机布局中的位置 ID 一致 |
| `status` | `occupied` 是确认有棋子，`empty` 是确认空位，`unknown` 是未确认 |
| `hero_id` | 有棋子时使用 `configs/inkborn_fables.json` 中的 ID，不填昵称或 OCR 原始文字 |
| `star` | 有棋子时填确认的一星 `1`、二星 `2` 或三星 `3`；无法确认则为 `null` |
| `cost` | 初始棋盘/备战席可留 `null`，不影响按星级统计副本；商店售价由实时 OCR 读取 |
| `confidence` | 已人工核对的明确事实填 `1.0`；未知保留 `0.0`，不要提高分数掩盖未知 |
| `source` | 已核对位置可填 `manual_reviewed`；模板保留 `template` |
| `ordinary_merges` | 只有确认该模式采用普通三合一并理解追踪限制后，才将 JSON 布尔值设为 `true` |
| `reviewed`、顶层 `source`、`notes` | 供人审阅的记录信息，建议写清当前对局及核对时点；它们本身不会替代位置事实或自动产生完整性 |
| `version`、`observed_at` | 模板用 `0`；运行时会将导入基线重置到本次进程的版本和时间起点 |

不要手填 `owned_copies`、`owned_star_counts`、`ownership_complete` 或 `bench_free` 来强行绕过未知。这些汇总应由位置事实和确认事件计算。当前导入器也不会把手写“完整”声明作为缺失位置的证据。

## 填写示例

以下只是两个位置的格式示例，**不是一份可执行的完整初始持牌**：

```json
{
  "board_0": {
    "slot": "board_0",
    "status": "occupied",
    "hero_id": "senna",
    "star": 2,
    "cost": null,
    "confidence": 1.0,
    "observed_at": 0,
    "source": "manual_reviewed"
  },
  "board_1": {
    "slot": "board_1",
    "status": "empty",
    "hero_id": null,
    "star": null,
    "cost": null,
    "confidence": 1.0,
    "observed_at": 0,
    "source": "manual_reviewed"
  }
}
```

二星赛娜占 3 张基础副本，只写在它实际所在的一个位置；不要再虚构另外两个赛娜位置。霞和洛都使用 `xayah_rakan`，记录实际站在棋盘或备战席上的那一个单位。召唤物和词典之外的英雄保持未支持，不能替换成相似英雄。

位置编号必须与自己校准的布局一致，当前代码不会从 JSON 键名自动知道哪一格在屏幕的哪一侧。推荐把己方四排、每排七格按从后排到前排、每排从左到右建立 `board_0` 至 `board_27`，备战席从左到右建立 `bench_0` 至 `bench_8`；这是**推荐的人工编号约定**，不是系统已自动识别的棋盘坐标。若采用其他约定，初始化文件与布局必须保持一致。

## 核对与使用

1. 选择当前真实对局的准备间隙，返回自己棋盘。核对 28 个棋盘位置和 9 个备战席位置；没有确认的格子继续保留 `unknown`。
2. 将已确认有牌的英雄 ID 和星级填写到对应位置；将亲眼确认的空位明确填写 `empty`。仅有详情英雄名、没有星级证据，不能填写确定星级。
3. 确认普通合成规则适用后设置 `ordinary_merges=true`。如果有改变升星、复制、占位或发牌方式的机制，需要先适配事件规则；不能仅靠这个开关宣称支持。
4. 核对期间若买牌、卖牌、获得棋子、复制或更换对局，基线必须重新检查。实时游戏不会因为编辑文件而暂停，不应把过时快照标成当前事实。
5. 完成窗口、文字区域、玩家身份和点击位置校准后，先运行观察模式检查等待原因和拟执行动作。

在仓库根目录用 PowerShell 执行。下面的窗口句柄是占位符，需要换成 `windows` 命令列出的真实游戏窗口句柄：

```powershell
.venv\Scripts\python.exe -m jcc_agent windows
.venv\Scripts\python.exe -m jcc_agent live --hwnd 0x实际窗口句柄 --layout configs/local.layout.json --self-state configs/local.inventory.json --duration 30 --out artifacts/live-observe
```

省略 `--execute` 时不会点击游戏。观察日志位于对应输出目录的 `events.jsonl`；查看 `ownership_complete`、`owned_copies`、`owned_star_counts`、`bench_free` 以及动作 `reason`。只有 37 个位置都已可信确认，才会建立完整汇总。运行时还会检查商店、售价、金币、阶段、时间、身份与详情关闭状态，填写持牌基线不能代替这些前置条件。

实际执行是在同一命令上增加 `--execute`，并使用新的输出目录。若 `ordinary_merges` 未明确为 `true`，导入基线的执行模式会在开始操作前拒绝。全未知模板即便被错误改为 `ordinary_merges=true`，持牌仍不完整，执行模式会在启动检查被拒绝。

## 购买之后怎样跟踪

只有控制器返回 `confirmed` 的购买才会使副本数增加；待确认、失败、观察模式的模拟动作都不改变持牌。已确认事件去重，避免重复处理同一次购买。

普通合成按照已知星级计数进行三进位：例如两张一星加一次购买，变为一张二星；三个二星变成一个三星。总基础副本数不因合成而减少。新棋子落点或合成后保留位置不确定时，位置记录可以变为未知，但一致的总副本账本仍可用于判断是否买够。

`bench_free` 是可证明空位数的**保守下界**，不是未经观察的实际空位数。购买后先按占用一个备战位扣减，再用完整星级账本修正：设 `P` 为全部已确认物理棋子数，`B` 为仍可信、未超过 60 秒且未因购买或合成而失效的棋盘位置数，则备战席至多有 `P-B` 个棋子，至少有 `max(0, 9-(P-B))` 个空位。程序取这一结果与已有下界中的较大值。

例如，三张一星确认合成一个二星后，即使落点未知，若总共只持有这一个物理棋子，也至少能证明备战席有八个空位，可以继续追牌；程序不会因此伪造八个具体空格。已过期或合成后位置未知的棋盘单位不计入 `B`。此推导依赖完整持仓账本及普通棋盘、备战席规则；出现未知授予、特殊合成或位置冲突时会停用汇总。现实里可用空位仍可能多于下界，必要时补充可信观察，不能手调汇总掩盖未知。

自行卖牌、移动、领取未知数量棋子、使用复制器或触发尚未建模的机制，都可能使账本失效。若程序没有取得这些事件的可信确认，应停止自动买牌、重建当前基线。程序不会保证通过稀疏 OCR 自动发现所有外部操作。

后续需要解决的是：在保持纯 OCR 的前提下找到可靠的星级/占位文字入口，或获得完整、可验证的初始化事件序列；如果这些信息在界面上根本没有文字，必须重新讨论输入范围。当前人工基线的作用是让交易与策略闭环可验证，不应作为“从任意对局画面自动接管”的完成证明。

## 当前视角声明

模板的 `ui_context_reviewed=false`、`viewed_player=unknown` 不授权默认自己。仅在核对当前自己的棋盘后，才同时设置 `ui_context_reviewed=true`、`viewed_player=self`。上下文会保留人工来源和原时刻；尝试导航后失效，不能用于猜测对手身份。执行期间外部键鼠或失焦会停止。启动前还需人工打开商店，当前 OCR 尚不能正向识别商店关闭状态。
